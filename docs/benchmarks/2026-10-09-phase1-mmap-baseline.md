# Phase 1 Baseline — MmapHandle (audit task 1.1) — 2026-10-09

First authoritative recording of `pdtk_bench_mmap` (landed with task 1.1).
Every number below comes from one single invocation of the binary
(single-invocation rule, ADR-0005).

## Command

```bash
cmake --preset release -DPython3_EXECUTABLE=$(which python)
cmake --build --preset release
scripts/run_perf.sh --json build/release/native/benchmarks/reports \
                    build/release/native/benchmarks/pdtk_bench_mmap
# perf stage: SKIPPED (perf not installed in this environment; U-010)
```

## Environment

* Reference sandbox: kata-containers VM, virtualized Intel Xeon, 2 vCPU,
  3200 MHz nominal, 4 GiB memory cgroup; `/tmp` on the container overlayfs
  (disk-backed — no tmpfs shortcut).
* GCC 14.2, `-O3 -march=native -DNDEBUG`, C++20; google/benchmark
  **v1.9.5** (FetchContent pin); corpus = 128 MiB deterministic LCG
  bytes written to a fresh mkstemp file per benchmark.
* The traversal loop (byte-sum) is **vectorized** — verified in the
  control experiment below (`vpaddq`/`vpmovzxdq`, ymm).

## Numbers

### `MmapHandle/sequential_read_128MiB` (20 repetitions)

Steady-state traversal of a warm, live mapping (the engine's hot loop).

| metric | value |
|---|---|
| mean | 53.70 ms |
| P50 (nearest-rank) | 51.37 ms |
| P90 | 65.14 ms |
| P99 | 65.88 ms |
| CV | 14.9 % |
| throughput | mean **2.55 GB/s** (min 2.04, max 3.11) |

The per-repetition distribution is wide and effectively bimodal in this
environment (~43–50 ms vs ~65 ms clusters) — see method notes.

### `MmapHandle/map_and_first_touch_128MiB` (20 repetitions)

Per-pass lifecycle: open + fstat + mmap + first touch of every page
(minor faults; page cache pre-warmed) + munmap + close.

| metric | value |
|---|---|
| mean | 69.18 ms |
| P50 | 68.97 ms |
| P90 | 73.21 ms |
| P99 | 74.00 ms |
| CV | 4.2 % |
| throughput | mean **1.94 GB/s** (min 1.81, max 2.11) |

### `MmapHandle/open_map_advise_close_1MiB` (1 sample)

Syscall path only, no data access: open + fstat + mmap +
posix_madvise(WILLNEED) + munmap + close = **4.59 µs** per lifecycle.
Single sample (no `Repetitions(20)` — a distribution claim is not made
for this one).

## Method notes (needed to interpret the numbers honestly)

1. **The environment, not the mapping, is the throughput ceiling.**
   A control experiment (same byte-sum over a 128 MiB *anonymous heap
   buffer*, 10 reps) measured **2.40–2.85 GB/s** — i.e. even pure memory
   traversal in this sandbox cannot exceed ~2.9 GB/s. The warm mmap run
   (2.20–2.48 GB/s in the same control) retains **~88–90 % of heap
   traversal speed**, which is the durable, environment-independent
   statement: zero-copy mapping costs roughly 10–12 % versus a heap
   buffer of the same size, and everything below that is the sandbox's
   shared-vCPU bandwidth.
2. **Absolute GB/s numbers from this sandbox must not be cited as
   engine capability.** They characterise the machine, not the code
   (see also U-012: the audit's later throughput gates — lexer 2.5 GB/s,
   scanner 4.0 GB/s — sit at or above this environment's raw ceiling).
3. **Warm page cache by design**: `sequential_read` pre-touches the
   mapping outside the timed region; `map_and_first_touch` pre-warms the
   page cache with a throwaway mapping so iteration 1 has no cold-disk
   skew. Cold-disk throughput is deliberately NOT measured — with a warm
   cache it cannot be measured honestly on this setup.
4. **Percentiles** are nearest-rank over the 20 per-repetition samples
   (`run_type == "iteration"` in the JSON report; google/benchmark
   v1.9.5 has no native percentile output — policy:
   `docs/benchmarks/README.md`).
5. The `map_and_first_touch` vs `sequential_read` gap (69.2 vs 53.7 ms
   mean, +29 %) is the per-byte page-fault + syscall cost of ingesting a
   fresh mapping — the number the Phase-2 parser ingestion path should
   be compared against.
6. Report file: `build/release/native/benchmarks/reports/pdtk_bench_mmap.json`
   (regenerated by the command above; not committed — recordings are).
